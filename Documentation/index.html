Lib3MFToolpath4EOS library guide

Overview

Lib3MFToolpath4EOS connects 3MF to EOS laser powder bed fusion machines. It drives an installed EOSPRINT API ("EOS SDK") at runtime and adds 3MF support on top of it. The library file is lib3mftoolpath4eos.dll; the API uses the namespace Lib3MF4EOS. With the library you can:

  • convert mesh 3MF files into EOS OpenJZ jobs and back,
  • compute EOS toolpaths through the EOS Toolpath API and store them in a 3MF with the 3MF Toolpath extension,
  • turn a toolpath 3MF back into an EOS task,
  • create EOS tasks, estimate build times and upload tasks to machines,
  • read and write raw EOS tasks layer by layer.

It has a C interface generated by the Automatic Component Toolkit (ACT), with bindings for C, C++, C#, Go, Java, Node.js, Pascal and Python. It does not ship any EOS binaries: the EOS SDK binding loads EosprintApi.dll from an existing installation when it is first needed. The headers of the EOSPRINT API and the EOS Toolpath API in Libraries/EOSSDK are copyright EOS GmbH, are shipped with the permission of EOS GmbH, and are only used at build time.

An agreement with EOS and authorization are required. Computing toolpaths (ComputeToolpathFrom3MF, ComputeToolpathFromOpenJZ) and creating tasks from toolpaths (CreateTaskFrom3MFToolpath) use the EOS Toolpath API. Access requires an agreement with EOS GmbH, under which EOS may assign a client ID and client-side encryption key. EDN membership is mandatory, and access is reserved for selected partners; there is no entitlement to access. Lib3MFToolpath4EOS does not grant any rights to the Toolpath API.

EOS process data must not be made accessible to third parties. The EOS agreement prohibits making EOS process data - including parameters, vector data, and energy input data - accessible to third parties in human- or machine-readable form. This includes EOS toolpaths and 3MF files containing EOS process data, such as output from WriteResultTo3MFFile. Do not distribute or otherwise make such data or files accessible to other, unauthorized parties or the public. These restrictions apply to EOS processes (original or customized), not to exposure strategies developed entirely by Toolpath API users themselves. The agreement defines the binding terms and scope of use.

The client-side key is confidential. The client-side encryption key assigned by EOS is a confidential credential, even though RSA libraries may refer to it as a "public key" and it is provided in PEM format. Do not ship it as a file alongside an application or check it into a repository. Protect it from unauthorized access. The examples store it in the Windows Credential Manager; see Toolpath API client key.

Requirements

  • Windows x64.
  • An installed EOSPRINT 2 or EOSPRINT API (SDK) of a supported version: 2.18 or 2.26. Without an explicit directory, Lib3MFToolpath4EOS searches the supported versions from newest to oldest; for each it tries C:\Program Files\EOS\EOSPRINT 2\2_xx first and then C:\Program Files\EOS\EOSPRINT 2 SDK\2_xx\bin\x64\release.
  • For toolpath computation: an agreement with EOS GmbH for the Toolpath API, the client ID and client-side encryption key assigned under it, and an SDK version that contains the Toolpath API.
  • An EOS material set (.eospar) and a machine configuration (machine package file or configuration directory) for everything beyond file conversion.

Loading the libraries

Lib3MFToolpath4EOS works on Lib3MF models. The application loads both libraries and hands its Lib3MF instance to Lib3MFToolpath4EOS, so that both use the same Lib3MF objects. With the dynamic C++ bindings (include/LibEOS/CppDynamic and include/Lib3MF/CppDynamic):

#include "lib3mftoolpath4eos_dynamic.hpp"
#include "lib3mf_dynamic.hpp"

auto pLib3MF = Lib3MF::CWrapper::loadLibrary("lib3mf.dll");
auto pLibEOS = Lib3MF4EOS::CWrapper::loadLibrary("lib3mftoolpath4eos.dll");
pLibEOS->InjectComponent("Lib3MF", pLib3MF->GetSymbolLookupMethod());

In Python, put Lib3MF4EOS.py and Lib3MF.py on the path; the Lib3MF4EOS binding imports the Lib3MF binding from its own folder:

import Lib3MF4EOS, Lib3MF

lib3mf = Lib3MF.Wrapper("lib3mf")
libeos = Lib3MF4EOS.Wrapper("lib3mftoolpath4eos")
libeos.InjectComponent("Lib3MF", lib3mf.GetSymbolLookupMethod())

The EOS context

All work happens on an EOSContext:

// Empty SDK directory: auto-detect. Empty log file name: a temporary log file is used.
auto pContext = pLibEOS->CreateContext("", "");
std::cout << pContext->GetDetectedAPIVersion() << " from " << pContext->GetSDKFilePath() << std::endl;

The SDK is loaded on first use. A few settings must happen before that:

  • EnableSDKSimulation(SimulateConnectivity) simulates the machine connection. A simulated machine cannot deliver its configuration, so load one explicitly.
  • SetCacheDirectory sets the EOS cache directory.
  • SetSDKVersionOverride(Major, Minor) forces the structure set of an SDK version instead of the detected one; 0, 0 removes the override. With full SDK simulation and no SDK installed, the override selects the simulated version.

SDK versions. The structures of the EOSPRINT API differ between SDK versions. Lib3MFToolpath4EOS detects the product version of the loaded EosprintApi.dll (through Eos_GetProductVersion where the SDK exports it, otherwise from the version resource of the DLL) and uses the declarations of the matching version. An unknown newer version uses the nearest lower known version; a version below 2.18 is refused. After loading, GetSDKProductVersion returns the detected version, GetSDKAdapterVersion the declarations in use, GetSDKVersionMessages the notes from the selection (override used, fallback to a lower version, version not detectable), and GetSupportedSDKVersions the known versions. LoadSDK and GetDetectedAPIVersion return the product version, for example 2.18.1149.0.

The context holds one job and one active machine configuration at a time. Functions that need a job load it themselves (for example ComputeToolpathFrom3MF); the job functions (LoadJobFrom3MF, CreateTask, ...) work on the current job.

Futures

Loading machine configurations, connecting, creating tasks, computing toolpaths, estimating build times and uploading run in the background and return a Future:

auto pConfig = pContext->LoadMachinePackageFromFile("M290.eosmachineinformation");
while (pConfig->IsRunning())
	std::this_thread::sleep_for(std::chrono::milliseconds(200));

if (pConfig->HasFailed())
	throw std::runtime_error(pConfig->GetErrorMessage());

Use WaitFor(milliseconds) instead of polling, and Abort() to stop the operation. Task creation, toolpath computation and build time estimation report the current and total layer count through GetProgress; uploads report a value from 0 to 1.

3MF and OpenJZ

Read 3MF files with the material set relationship registered; otherwise Lib3MF drops the attachment:

auto pModel = pLib3MF->CreateModel();
auto pReader = pModel->QueryReader("3mf");
pReader->AddRelationToRead(pContext->GetMaterialSetRelationshipType());
auto pSource = pModel->CreatePersistentSourceFromFile("part.3mf");
pReader->ReadFromPersistentSource(pSource.get());

pContext->AttachMaterialSetTo3MF(pModel, "316L_040_FlexM291.eospar");   // if the file has none
pContext->Convert3MFToOpenJZ(pModel, "part.openjz");

Lib3MFToolpath4EOS takes the machine target, parameter set, material and layer thickness from the embedded material set. The eos3mf metadata of the model (see 3MF conventions) overrides these values; without a material set, all of them must be present.

The OpenJZ writer bakes every part's transformation into its mesh, writes the mesh relative to its bounding box minimum and stores the minimum as translation. Parts keep their Z position, so they stay aligned with the toolpath layers; a part below Z = 0 is refused by the EOS SDK (EOS_ERR_STL_BELOW_PLATFORM).

ConvertOpenJZTo3MF reads the STL geometry (binary or ASCII), part placement (translation, Z rotation, scaling, coordinate origin), part parameters, support flags and the OpenJZ's material set. Segmented geometry is not supported.

Toolpaths

Toolpath computation needs Toolpath API credentials and a machine configuration:

// The client key is stored as a generic Windows credential (see toolpath_credential in the examples).
pContext->AuthenticateToolpathAPIFromCredentialStore(nClientID, "LibEOS-TPAPI");
// Or pass the PEM text yourself: pContext->AuthenticateToolpathAPI(nClientID, sClientKeyPEM);
auto pComputation = pContext->ComputeToolpathFrom3MF(pModel, pConfig);
// wait for the future ...
pComputation->WriteResultTo3MFFile("part.toolpath.3mf");

The toolpath 3MF contains the toolpath (one profile per distinct laser setting, one layer file per layer), the part meshes, the job metadata and the material set. WriteResultTo3MF fills a model and writer you provide instead, and LoadRawTask gives access to the computed EOS layers.

The export also keeps what the EOS task says beyond the vectors. Each EOS scanner is declared as a laser source (laser indices 0 to N-1, matching the profiles' laserindex). The layers are read from the task's first EOS layer (EOSRawTask.GetFirstLayerIndex). A task that starts above the build plate gets a toolpath bottom Z one layer thickness below its first layer. A delay becomes eos:predelay in the profile of the segment that follows it; a delay at the very end of a layer has no following segment and is not written. Every segment carries the EOS timestamp of its first point and its stripe number as custom segment attributes (see Segment attributes).

CreateTaskFrom3MFToolpath goes the other way: it loads the job from the model's meshes, writes each toolpath layer into a raw EOS task and converts it into a machine task. Hatch segments become hatch blocks, loops and polylines become polyline blocks; the EOS parameters come from the profiles. A profile without eos:exposuretype gets exposure type 2 (infill) for hatches and 10 (simple contour) for polylines and loops; without eos:skywriting, skywriting follows the settings (default on). Layers without exposure are not written, and each skipped layer is logged with its Z.

Each part's layer thickness is derived from the toolpath layers it has vectors in, and the layer Z values are read as layer tops or bases according to the settings (see layer Z and thickness). A part without eos3mf:partparameter gets the exposure set that the settings assign to its layer thickness (SetExposureSetForThickness), else the only exposure set of the material set with that thickness and the part's support flag. If none or several match, the conversion is refused with EXPOSURESETAMBIGUOUS, unless SetAllowDefaultExposureSets permits _Default_DirectPart or _Default_ExternalSupport. Each choice is logged. The OpenJob of the job is written in the version of the loaded SDK's declarations (1.5.22 for 2.18, 1.5.23 for 2.26), and its height ends at the Z of the top toolpath layer. Mesh conversions (Convert3MFToOpenJZ, LoadJobFrom3MF, toolpath computation) keep the _Default_ parameters for parts without eos3mf:partparameter.

Before writing layers, the toolpath is checked against the layer stack and process heights that the EOS SDK computes for the job. CheckLayerCoverage runs this check alone, and CheckPartToolpathAlignment compares the meshes with their toolpath; see pre-flight checks.

Build item and component transforms move the meshes only. Toolpath coordinates are written as they are, so a toolpath 3MF must have its build items untransformed, or the toolpath must already contain the transform. Lib3MFToolpath4EOS does not check this.

Laser power ramps

A laserpower modifier on a profile lets the power change along a hatch or polyline (constant, linear or nonlinear factors). EOS sets the power per vector, so Lib3MFToolpath4EOS splits a ramp into sub-vectors of constant power, each at the mean power of its interval. By default, a ramped hatch is written as one continuous polyline with a power change before every sub-vector, with at most 1 W between neighbouring sub-vectors and sub-vectors of at least 0.05 mm. Change this in the conversion settings:

auto pSettings = pContext->CreateToolpathConversionSettings();
pSettings->SetPowerRampMode(Lib3MF4EOS::eEOSPowerRampMode::SplitHatches);   // or Polyline, Flatten, Reject
auto pTask = pContext->CreateTaskFrom3MFToolpath(pModel, pConfig, pSettings, "part", "", "MyApp", "1.0");

The conversion page lists all settings and describes the conversion log that every conversion produces (GetConversionLog), also when it fails.

Factors must lie in [0, 1]. In strict mode (the default) a factor outside is refused with MODIFICATIONFACTOROUTOFRANGE; otherwise it is clamped and logged. A constant laserpower modifier on a polyline is a step: each vector gets the factor of the point it ends at. On a hatch, a constant modifier must have the same factor at both ends; different factors are refused with UNEQUALCONSTANTHATCH, or, if SetRefuseUnequalConstantHatch(false), the factor of the end is used and a warning logged. laserspeed and eos:focus work like laserpower, with all modifier types; their ramps are split by MaxSpeedStep and MaxFocusStep. A laserfocus modifier is rejected, because the mm offset has no EOS equivalent. The pulse times accept constant modifiers only: a hatch segment is split wherever the value changes, and a polyline must keep one value. Modifiers on other parameters are rejected, except postwaittime, see below; prewaittime is only written as a constant. Toolpaths computed by EOS keep their power changes: blocks with varying power are written with a laserpower modifier. The power ramp page describes the details.

Write rules

By default, touching hatches are joined into one polyline, and so are touching contours (SetHatchWriteMode, SetJoinContours, SetJoinTolerance). Every laser power change carries a delay of 190 µs (SetPowerDelay). With EOS SDK 2.26 and later, each scanner starts every layer with the standard beam shape and a 10 µs delay (SetLayerOpening); eos:beamshapeprofile selects a beam shape profile for a segment. The exposed depth is the job's layer thickness, unless the profile gives eos:exposeddepth.

eos:predelay and eos:postdelay add delays in µs before a segment and after each hatch or polyline. postwaittime is a dwell after every vector and prewaittime a dwell before every vector, both in the unit set with SetDwellTimeUnit; without a unit, toolpaths with dwell times are refused with DWELLTIMEUNITMISSING. The prewaittime before the first vector of a segment is written as its pre-delay, the others as dwells after the vector in front.

Profile parameters that Lib3MFToolpath4EOS does not write are never dropped silently: jumpspeed, which the EOS toolpath API cannot set, any other unknown parameter, and parameters in a namespace that is neither the EOS toolpath namespace nor a registered legacy one. In strict mode they are refused with PROFILEPARAMETERNOTSUPPORTED; otherwise each is left out with a PROFILE_PARAMETER_IGNORED warning.

If the toolpath declares laser sources, their laser indices are mapped in ascending order to the scanners 0 to N-1, and a segment with an undeclared laser index is refused with LASERINDEXUNDECLARED. Without laser sources, the laser index is the scanner index. A profile without laserindex uses the toolpath's default laser index. The mapping is logged.

A laser index that maps to a scanner the machine configuration does not have is refused with LASERSCANNERNOTAVAILABLE. In every layer, each scanner is selected once, in ascending order, and its blocks keep their order. The EOS task generator refuses a layer in which a scanner has no begun part (EOS status 87), so every scanner without work in a layer gets a part begun at its place in that order, with no exposure and no delay.

The task needs every exposed layer of the job's layer stack. A stack layer without toolpath, because the toolpath layer is empty or missing, is filled with a layer in which every scanner begins a part of that layer and exposes nothing (LAYER_FILLED). If some toolpath layers are not on the stack, nothing is filled (LAYER_FILL_SKIPPED). The EOS SDK reports the job's Z shrinkage compensation but cannot apply it to a toolpath: a non-zero compensation is refused in strict mode with SHRINKAGECOMPENSATIONNOTSUPPORTED, and otherwise logged as a warning while the toolpath is written at its own Z.

EOS lasers run their commands independently, and an EOS task has no barrier between them: in strict mode, lasersync and sync or delay segments are refused with LASERSYNCNOTSUPPORTED; otherwise lasersync is ignored with a warning. A producer that needs the lasers to start a phase together can give the first segment of each waiting laser a profile with eos:predelay: it is written once, on that laser, and the segment is never joined to the one before it.

Toolpath layers are read lazily. Read toolpath 3MFs with ReadFromPersistentSource and keep the persistent source alive while Lib3MFToolpath4EOS works on the model. ReadFromFile closes the file, and reading layers later fails with "Data source is invalidated".

Tasks and machines

auto pSession = pContext->ConnectToMachine("192.168.0.10");
// wait ...
auto pConfig = pSession->DownloadMachineConfig();
// wait ...
pContext->LoadJobFrom3MF(pModel);
pContext->ActivateMachineConfiguration(pConfig);

auto pTask = pContext->CreateTask("part", "comment", "MyApp", "1.0");
// wait ...
auto pUpload = pSession->UploadTask(pTask);
// wait ...

TaskCreationFuture::StoreInDirectory keeps a copy of the task; UploadTaskFile uploads an existing task file together with its data files. Machine configurations can also come from a package file (LoadMachinePackageFromFile), memory (LoadMachinePackage) or a configuration directory (LoadMachineConfigFromDirectory), and can be saved with StorePackageInFile. ReadMachineInformation reports the machine type, build volume, serial number and laser count, and per laser scanner its scan field (GetLaserScannerField), power and speed limits (GetLaserScannerLimits) and capabilities (GetLaserScannerCapabilities). A model type that Lib3MFToolpath4EOS does not know is reported as Unknown; GetModelTypeProductName then gives its number and only GetModelTypeIdentifier fails.

Raw tasks

Raw tasks give direct access to the exposure data. CreateRawTask computes one from the current job; TaskCreationFuture::LoadRawTask then opens it for reading layer by layer (EOSRawTaskLayer: points and blocks).

To write exposure data yourself, create a writer with CreateRawTaskWriter(pSettings), fill layers created by CreateEOSRawTaskLayer with AddData, write them with strictly increasing layer index and Z height and finish with ConvertToTask. A job and machine configuration must be active.

Every point carries its own LaserPower and ScanSpeed; values of 0 or less use the block's values. Its LaserFocus is used if HasLaserFocus is true, otherwise the block's if its HasLaserFocus is true; without either, the scanner stays fully focused and no focus command is written. Focus values go from 0.0 (fully defocused) to 1.0 (fully focused). In a hatch block, the values ramp linearly from the first to the second point of a hatch, and the writer applies the power ramp settings and the joining rules. In a polyline block, a point's values are those of the vector that ends at it. A block's PostDelay is written after each hatch or after the polyline, and BeamShapeProfile (-1 for none) sets the beam shape with EOS SDK 2.26; older SDKs fail on a profile above 0 in strict mode and otherwise leave it out with a warning. The writer's GetConversionLog counts what was written.

Segment attributes

The EOS to 3MF export writes two custom segment attributes in the namespace http://schemas.3mf.io/eos/toolpath/2026/11. To read them with lib3mf, register them on the toolpath with RegisterCustomDoubleSegmentAttribute and RegisterCustomIntegerSegmentAttribute before calling ReadLayerData. CreateTaskFrom3MFToolpath ignores them.

AttributeTypeMeaning
timestampdoubleEOS time of the segment's first point in µs, exactly as the EOS SDK reported it. For a polyline that was cut where speed or focus change, it is the time of the joint the part starts at.
stripeintegerNumber of the EOS stripe segment within the layer, counted from 1; 0 for segments outside a stripe.

Machine packages

Machine packages use the namespace http://schemas.3mf.io/eos/machinepackage/2026/11.

Legacy namespaces

Lib3MFToolpath4EOS always writes the current schemas.3mf.io/eos namespaces. When reading, it also accepts any legacy namespace registered with RegisterLegacyNamespace(Kind, NamespaceURI). Registrations apply to the context and to the futures and loaders it creates afterwards, and the current namespace always wins when a value is present under both. GetNamespace(Kind) returns the current namespace and ClearLegacyNamespaces() removes all registered ones.

Reading a 3MF with a legacy material set relationship type additionally requires the host to add that type to its lib3mf reader with AddRelationToRead, because lib3mf drops attachments whose relationship type is not registered before reading.

Part numbering

Parts are numbered 1..N in build item order, depth first through component objects. OpenJZ part IDs, EOS task part IDs and toolpath part references all use this numbering.

Errors

Every failing call reports an error code and message; the C++ bindings throw Lib3MF4EOS::ELib3MF4EOSException. Failures inside futures are reported by HasFailed and GetErrorMessage. The codes are listed in the API reference. Worth knowing:

  • COULDNOTFINDEOSSDKDIRECTORY: no SDK found; pass the directory to CreateContext.
  • COULDNOTLOADLIBRARY: Lib3MF was not injected with InjectComponent.
  • TOOLPATHSDKNOTSUPPORTED: the loaded SDK lacks a toolpath function the operation needs. Older SDKs are detected: optional values are skipped while reading, and writing a value that needs a missing function fails with this error.
  • EOSSDKERROR: the EOS SDK reported an error; the message contains its description.

Building and packaging

cmake -S . -B build
cmake --build build --config Release

This builds lib3mftoolpath4eos.dll and the examples (disable them with -DLIBEOS_BUILD_EXAMPLES=OFF). Visual Studio 2022 or newer and CMake 3.10 or newer are required.

The binary release ZIP is created by

powershell -ExecutionPolicy Bypass -File Scripts\create_release.ps1

or, in an existing build directory, by cmake --build build --config Release --target package.

The API is defined in ACT/Lib3MFToolpath4EOS.xml. After changing it, regenerate the bindings with ACT/generate.bat and this reference with python Scripts/generate_api_reference.py.
